1. PRODUCT OVERVIEW
Settlebook is a lightweight mobile-first web application and installable Progressive Web App (PWA) designed to help users manage money owed between people.

The application has three primary financial workflows:

Individual Ledger: Track money given, money taken, outstanding balances, repayments, and transaction history between two people.
Split Bills: Divide an expense among multiple participants, either equally or using custom amounts, and create the corresponding financial obligations.
Groups: Maintain a temporary, isolated ledger containing multiple expenses and participants. Calculate net obligations and transfer them into the individual/shared ledger system only when the group is finalized.
These three workflows must work together without double counting, incorrect balances, duplicate records, or inconsistent synchronization.

The application must be simple enough for everyday use, but its financial accounting must be reliable.

All monetary calculations must be performed using integer minor units (cents), never binary floating-point arithmetic.

The default currency is AUD. Design the database so additional currencies can be supported later, but do not introduce currency conversion into the MVP.

Accounting Rules

8. SPLIT BILLS
Users can create a bill involving multiple participants.

Bill fields:

Description
Total amount
Currency
Payer
Participants
Split method
Optional attachment
Date
Notes
Equal Split
Divide the total equally among selected participants.

Use integer cents and deterministic remainder allocation.

Example:

$100 divided among three people must produce:

$33.34 + $33.33 + $33.33 = $100.00

Never lose or create money through rounding.

Custom Split
Allow manual share allocation.

The sum of participant shares must equal the bill total.

Reject invalid totals.

Payer Handling
The payer may be:

The current user
Another registered user
An unregistered contact
Support obligations between any participating pair.

Do not incorrectly attribute third-party debts to the current user.

For example:

Sahil pays $90 for Sahil, Priya, and Bhushan.

Each person's share is $30.

The system must correctly create:

Bhushan owes Sahil $30.
Priya owes Sahil $30.
Sahil owes himself nothing.

Posting
Split bills outside groups create financial obligations in the appropriate individual/shared ledgers.

The bill and its resulting obligations must remain linked.

Posting must be atomic and idempotent.

Critical Isolation Rule
No group expense may modify an individual ledger while the group remains open.

Group balances must be calculated independently.

Example:

A group has four members.

Sahil pays $200 for accommodation.
Bhushan pays $80 for food.
Priya pays $60 for transport.
Alex pays $40 for groceries.
The group calculates each member's contribution and obligation.

Individual ledgers remain unchanged until finalization.

Settlement Calculation
Calculate:

Total group spending
Amount paid by each member
Amount owed by each member
Net creditor/debtor position
Recommended settlement transfers
Use a deterministic debt simplification algorithm.

The algorithm should reduce unnecessary transfers without changing the total amount owed.

Do not falsely claim mathematical minimum-transfer optimality if the implemented algorithm only provides a practical reduction.

Group Review
Before finalization:

Show every expense.
Show each participant's share.
Show the settlement preview.
Allow members to acknowledge or dispute entries.
Display unresolved disputes.
Allow the creator to correct expenses while preserving audit history.
Group Finalization
Only the creator or an explicitly authorized administrator can finalize the group.

Before finalization:

Validate expense totals.
Validate membership.
Validate all share allocations.
Recalculate settlement.
Check unresolved disputes.
Present a final confirmation.
Record a finalized snapshot.
Upon finalization:

Freeze the group.
Calculate the final net obligations.
Generate corresponding individual/shared ledger obligations.
Link those obligations to the group.
Commit the operation atomically.
Mark the group finalized.
Notify affected users.
Do not create duplicate obligations if the finalization request is retried.

A finalized group must not be silently modified.

Any subsequent corrections require an explicit audited adjustment workflow.

Settlement Semantics
Finalizing a group means the obligations have been transferred to the individual/shared ledger system.

It does not mean that money has physically changed hands.

Users can later record repayments through their individual ledgers.

The system must correctly support obligations between all members, including pairs that do not involve the group creator.
